## How Binary Compilation Works

The desktop app ships as a **Tauri 2 shell** (Rust) that launches two **PyInstaller onedir executables** (flowfile_core + flowfile_worker) as child processes ("sidecars"). The full pipeline:

```
poetry install --with build
    → PyInstaller builds two .spec files (one per service)
    → Each produces services_dist/<name>/<name> + services_dist/<name>/_internal/
    → combine_packages() merges both _internal/ into one shared services_dist/_internal/
    → prune_locales() + prune_unused_data() strip ~100MB of bloat
    → tools/rename_sidecar.py copies executables → src-tauri/binaries/<name>-<triple>
    → tools/rename_sidecar.py copies _internal/ → src-tauri/binaries/_internal/
    → npm run build (Tauri) bundles binaries/** as resources into the app installer
```

At runtime, the Rust shell (`sidecar/mod.rs`) resolves `binaries/<name>-<triple>` from the resource dir, spawns both processes, waits for health checks on their ports, and manages crash recovery.

## Why This Works

- **shapely ≥2.0** bundles GEOS as a vendored DLL/dylib/so inside the wheel (`shapely/libgeos_c.so` / `geos_c.dll`). `collect_dynamic_libs('shapely')` picks it up.
- **fiona ≥1.10** bundles GDAL + PROJ as vendored native libraries inside the wheel (`fiona/.dylibs/` on macOS, `fiona.libs/` on Linux, DLLs in the package on Windows). `collect_dynamic_libs('fiona')` + `collect_data_files('fiona')` picks up both the native libs and the PROJ datum grid files.
- No system-level `apt-get install libgdal-dev` is needed for the desktop build — the wheels are self-contained on all three platforms (unlike Docker where we install system packages for the slim base image).
